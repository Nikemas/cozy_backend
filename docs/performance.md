# Производительность БД на росте (perf/db-at-scale)

Цель: магазин должен оставаться быстрым при ~5 000 товаров, ~60 000 вариантов,
остатках по 5 точкам, ~30 000 покупателей и ~100 000 заказов (~200 000 строк
заказов). Пороги: p95 ≤ 150 мс для API, ≤ 300 мс для страниц сайта/админки и
отчётов при 20 параллельных запросах.

## Набор данных

`scripts/perf/seed.sql` генерирует данные поверх пустой БД с применёнными
миграциями. Он детерминирован (`setseed`, id = `md5('<kind>-<n>')::uuid`) и
отказывается работать, если в имени БД нет `perf` или каталог не пуст.

| Таблица | Полный объём (по умолчанию) | Измеренный прогон |
|---|---:|---:|
| products (≈92% активных) | 5 000 | 2 000 |
| product_variants (размер × цвет) | ~60 000 | 24 006 |
| stock (5 точек, ~60% пар, ~25% нулевые) | ~180 000 | 71 914 |
| product_images | ~12 500 | 5 000 |
| customers (+80% с адресом) | 30 000 | 10 000 |
| orders (2 года, рост потока) | 100 000 | 30 000 |
| order_items (популярность по степенному закону) | ~200 000 | 60 028 |
| payments / order_status_history / favorites / cart_items | ~40k / ~190k / ~40k / ~8k | 12 077 / 59 919 / 13 309 / 2 666 |

Распределения: дерево из 4 корневых категорий × 7 подкатегорий (5% товаров
лежат прямо в корне), 30 брендов (частоты по Ципфу), цены 1 500–15 000 сом,
у 10% вариантов `price_override`. Статусы: свежие заказы — placed/confirmed/
courier_assigned, старые — 88% delivered и 12% cancelled; 40% оплачены онлайн.

**Важно про масштаб.** Измерения сделаны на **сокращённом** наборе
(`-v n_products=2000 -v n_customers=10000 -v n_orders=30000`, примерно 40% от
целевого объёма). Во время работы на машине кончилось место на диске
(посторонние данные), Postgres упал и восстановился, после чего прогон на
полном объёме не запускался. Сокращённый набор занимает 80 МБ, полный по оценке около
250 МБ. Поэтому в абсолютных цифрах ниже нужно учитывать масштаб.
Стоимость запросов, которые раньше были O(все строки заказов) (популярность,
отчёты, COUNT в списке заказов), на полном объёме растёт примерно в 3,3 раза;
после правок это либо поиск по ключу, либо работа O(товары в выдаче).

## Метод

* Сервер собирался из бинарника (`go build ./cmd/server`) и работал с
  `APP_ENV=dev RATE_LIMIT_RPS=0 PAYMENTS_PROVIDER=mock MINIO_BUCKET=cozy-perf`.
  В админке входили под владельцем, созданным через `server create-owner`.
* Нагрузка: `scripts/perf/loadtest` (замкнутый цикл, 20 воркеров по 20 с на
  каждый URL, выводит p50/p95/p99 и число ответов не 2xx). URL перечислены
  в `scripts/perf/targets.txt`.
* **Сравнение A/B в одно время.** Версии «до» (`main`, БД `cozy_perf`) и
  «после» (эта ветка, копия той же БД с миграциями 000042–000043) работали
  одновременно на :8096 и :8097, а прогоны шли попарно для каждого URL. Обе
  БД перед этим прошли `VACUUM ANALYZE`. Перед замерами для каждого URL
  проверялось, что ответы «до» и «после» **совпадают побайтно** (все 26 URL,
  включая HTML админки и xlsx/JSON отчётов).
* На машине одновременно шли другие сессии: load average колебался от 7 до 180
  при 10 ядрах (Apple M4). Цифры под нагрузкой поэтому шумные и подходят только
  для сравнения A/B, взятого в одно и то же время. Дополнительно указана медиана
  11 последовательных одиночных запросов: это стоимость самого запроса.

### Что осталось выше порога

* **/admin/reports под 20 параллельными запросами.** Один запрос страницы
  стоит 28 мс за месяц и около 260 мс за год (на полном объёме ожидается
  примерно 0,8 с). Это страница владельца: её открывает один человек, и
  20 параллельных годовых отчётов — нереалистичный сценарий. Пропускную
  способность ограничивает CPU Postgres на агрегации всех строк заказов за
  период. Без хранения агрегатов отдельно её не исправить. Варианты на будущее:
  1. Таблица `daily_sales` (день × точка × товар), которую ведут триггеры, как
     `product_sales`.
  2. Кэш результата отчёта с коротким TTL. Это меняет поведение: появляется
     окно устаревания.

  В этой ветке ни один из вариантов не сделан.

  **perf/report-cache: сделан вариант 2.** `reports.CachedRepo` — кэш в
  процессе перед `Sales`/`BrandSales`/`CategorySales` (и страница
  /admin/reports, и `/admin/api/reports/sales[.xlsx]`). Ключ — запрос +
  from/to + group_by + карта названий точек; ролей/точек/языка в ключе нет,
  потому что запросы их не принимают: отчёт общий по магазину и доступен
  только owner/manager. TTL 5 мин, если период целиком в прошлом, и 1 мин,
  если он включает сегодня; не больше 256 записей; ошибки не кэшируются;
  одинаковые параллельные запросы выполняют SQL один раз (singleflight),
  разных запросов одновременно не больше 4; паника в запросе становится
  ошибкой (500), а не роняет процесс.
  Окно устаревания — до 1 мин для текущего периода. Замер на уровне запросов
  (`go run ./scripts/perf/reportbench -db …`, тот же сокращённый набор,
  20 параллельных просмотров страницы за год): без кэша p95 ≈ 1 000 мс,
  первый всплеск с кэшем ≈ 175 мс (один набор запросов на всех), далее
  p95 ≈ 3–6 мс.
* `sitemap.xml` укладывается в порог страниц, но заметим: он перечисляет не
  больше `sitemapPageSize = 5000` товаров (`internal/web/sitemap.go`). Активных
  товаров в целевом объёме около 4 600, то есть запас небольшой. После
  5 000 активных товаров sitemap молча обрезается.

## Что изменено

Ни одна правка не меняет ответы: в интеграционных тестах SQL-версии сравниваются
с прежней логикой, а ответы всех 26 URL совпали побайтно.

1. **`sort=popular` → `product_sales` (миграция 000042).** Раньше каждый запрос
   агрегировал все `order_items JOIN orders JOIN product_variants` (O(строки
   заказов)). Теперь триггеры в той же транзакции поддерживают число продаж по
   товарам:
   * вставка, изменение и удаление строки заказа;
   * переход статуса в `cancelled` и обратно;
   * удаление заказа (BEFORE DELETE; каскадные удаления строк после этого
     пропускаются);
   * перенос варианта к другому товару.

   Сортировка точная, без окна устаревания, и сводится к соединению по PK.
   Чтобы не было взаимоблокировок, обновления нескольких товаров идут в
   порядке `product_id`, а checkout (`orders.Service.CreateOrder`) вставляет
   строки заказа в порядке товаров. Порядок захвата блокировок «сначала stock,
   потом product_sales» совпадает в checkout и при отмене заказа.
   Тест: `internal/integration/product_sales_test.go`.
2. **Индексы (миграция 000043, `pg_trgm`):**
   * `idx_product_variants_sku_trgm`: GIN-триграммы по SKU. Поиск по каталогу
     проверяет SKU для каждого слова запроса; раньше это был полный проход по
     вариантам на каждое слово, теперь поиск по индексу.
   * `idx_product_variants_product_price`: `(product_id) INCLUDE
     (price_override)`. Подзапросы цены (`minPriceExpr`/`maxPriceExpr`) для
     `sort=price_*` и фильтров цены выполняются только по индексу; на этих
     данных `price_asc` примерно втрое быстрее.
   * `idx_orders_number_trgm`, `idx_customers_phone_digits_trgm`: поиск в
     /admin/orders по номеру заказа и по цифрам телефона.
3. **Фасеты за один проход** (`catalog.ProductRepo.Facets`). Раньше было два
   запроса: DISTINCT размеров и цветов, плюс MIN/MAX с двумя коррелированными
   подзапросами на каждый товар. Теперь это один запрос `products LEFT JOIN
   product_variants GROUP BY size, color`. Товар без вариантов даёт строку с
   NULL и `base_price`, как и раньше.
4. **`in_stock`** (`catalog.buildListConditions`). Проверку остатка не даёт
   развернуть в semi-join ограничитель `OFFSET 0`. Иначе для COUNT на каждый
   запрос хешировалась вся таблица stock (O(варианты × точки)); теперь это
   проверка по PK `(variant_id, point_id)` до первого варианта в наличии.
5. **Список и поиск заказов в админке.** Убран `JOIN customers`: `customer_id`
   имеет `NOT NULL REFERENCES`, поэтому JOIN не отсекал строк, а лишь заставлял
   COUNT каждой страницы читать две таблицы. Поиск по телефону сделан
   подзапросом по `customers`: выражение считается по покупателям, а не по
   заказам, и может использовать триграммный индекс.
6. **Отчёты агрегируются в SQL** (`reports.Repo.Sales`; используется и
   страницей /admin/reports, и `/admin/api/reports/sales[.xlsx]`).
   * Раньше в память загружались все заказы и строки за период. Сейчас
     результат — несколько сотен строк, и память не растёт вместе с периодом.
   * Текстовые ключи (товар, бренд, категория) группируются с `COLLATE "C"`.
     Группы получаются те же, потому что сопоставление БД детерминировано, но
     сравнение идёт по байтам, а не локалью. Порядок вывода по-прежнему
     задаётся в Go, а в категориях — `COLLATE "default"`.
   * Дни группируются по значению `date` и форматируются после группировки.
   * `reports.AggregateSales` остаётся эталоном:
     `internal/integration/reports_sales_test.go` сравнивает с ним все
     группировки, включая границы суток по Бишкеку, точки с одинаковым
     названием и заказ без точки.

N+1 не найдено: все списки (каталог, админка, заказы) уже загружают фото,
цены, остатки и телефоны пакетами `= ANY($1)`. LIMIT есть везде, кроме
sitemap (там ограничение в 5 000, см. выше) и отчётов, где агрегат и так
небольшой.

### Про миграции

`CREATE INDEX` без `CONCURRENTLY`: golang-migrate выполняет каждый файл в
транзакции, а там `CONCURRENTLY` запрещён. На таблицах такого размера индекс
строится меньше чем за секунду, и короткая блокировка записи безвредна. Если
таблица когда-нибудь вырастет настолько, что это станет важно, индекс можно
заранее построить вручную с `CONCURRENTLY`; тогда `IF NOT EXISTS` превратит
миграцию в no-op. `pg_trgm` поставляется с Postgres, и с PG13 это доверенное
расширение: владелец БД может его создать (в `docker-compose*.yml` это
пользователь `cozy`).

## Как повторить

```sh
cd cozy_backend
DB=cozy_perf
createdb $DB
go run -tags postgres github.com/golang-migrate/migrate/v4/cmd/migrate@v4.18.3 \
  -database "postgres://$(whoami)@localhost:5432/$DB?sslmode=disable" -path migrations up
# полный объём (по оценке ~250 МБ); сокращённый набор генерируется ~10 с:
#   -v n_products=2000 -v n_customers=10000 -v n_orders=30000
psql -v ON_ERROR_STOP=1 -d $DB -f scripts/perf/seed.sql
psql -d $DB -c 'VACUUM ANALYZE'

go build -o /tmp/cozy-server ./cmd/server
read -rs PW && echo "$PW" | DATABASE_URL="postgres://$(whoami)@localhost:5432/$DB?sslmode=disable" \
  /tmp/cozy-server create-owner --phone +996555000999 --name Perf

APP_ENV=dev HTTP_ADDR=:8096 PUBLIC_BASE_URL=http://localhost:8096 \
  DATABASE_URL="postgres://$(whoami)@localhost:5432/$DB?sslmode=disable" \
  JWT_SECRET=$(openssl rand -hex 32) NIKITA_API_KEY=dev-unused SMS_MOCK_OTP=true \
  PAYMENTS_PROVIDER=mock RATE_LIMIT_RPS=0 MINIO_ENDPOINT=localhost:9000 \
  MINIO_ACCESS_KEY=cozy MINIO_SECRET_KEY=cozy12345 MINIO_BUCKET=cozy-perf \
  MINIO_PUBLIC_ENDPOINT=localhost:9000 /tmp/cozy-server &   # из cozy_backend/ (шаблоны)

curl -s -c /tmp/perf.cookies -H 'Origin: http://localhost:8096' -X POST localhost:8096/admin/login \
  --data-urlencode phone=+996555000999 --data-urlencode "password=$PW" -o /dev/null
go run ./scripts/perf/loadtest -base http://localhost:8096 -targets scripts/perf/targets.txt \
  -cookie "staff_session=$(awk '/staff_session/{print $7}' /tmp/perf.cookies)" -c 20 -d 20s
# один URL: -only api_products_popular

kill %1; dropdb $DB
```

Чтобы сравнить A/B, создайте вторую БД через `CREATE DATABASE … TEMPLATE
cozy_perf` до применения новых миграций и запустите вторую сборку на другом
порту. Для отдельного запроса план смотрите через
`EXPLAIN (ANALYZE, BUFFERS)`.
